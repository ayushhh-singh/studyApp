## 0d. ⛔ PRODUCTION INCIDENT — 2026-07-31: `ingest:syllabus` ran for real against the production DB, twice

**Permanent record. This is not resolved-and-forgettable — the standing warning at the bottom applies to every future session.**

**What happened.** An agent was dispatched to *test a newly-added guard* on `ingest:syllabus` and batched its invocations in a shell loop. **zsh does not word-split an unquoted `$a`**, so `--exam upsc --dry-run` reached the process as **ONE argv token**. `parseArgs` (`ingest/_shared.ts`) reads that as the nonsense KEY `"exam upsc --dry-run"`, which leaves `args.exam` **`undefined` — not `true`** — so the valueless-flag guard could not see it, `onlyExam` fell to `null`, the exam scope defaulted to `uppsc`, and **`--dry-run` was swallowed into the same nonsense key so `dryRun` was FALSE**. The result was a real, billed, LLM-structuring run that WROTE to the DB — which is **the same Supabase project for dev AND production**. It happened **twice**.

**Damage.** **+85 orphan rows** (`syllabus_nodes` 294 → 379) and **35 rows overwritten in place** (`title_i18n` / `description_i18n`). Row **ids were unchanged**, so 2,682 question references and 31 note references stayed structurally intact — the blast radius was text, not referential integrity. **The hand-authored UPSC tree (202 rows) was never touched: every explicit `--exam upsc` invocation was correctly REFUSED. The accident came in through the DEFAULT path, which no guard covered.**

**CA amplification, and it has a short fuse.** The phantom nodes entered `loadSyllabusCandidates`' triage candidate set, and a `ca:run` mapped a generated Article-338 MCQ onto one of them **within ten minutes**. `ca:run` is 6-hourly, so a repeat would have compounded quickly.

**Recovery, and the property that made it verifiable.** `backup.yml`'s weekly GPG-encrypted `pg_dump` had **4 successful runs** (its "this is new" header is **stale** — the workflow works); `supabase-backup-2026-07-26` predated the incident by 5 days. **The decisive detail: the backup predates migration `0106`, so its `syllabus_nodes` has no `exam_code` column and held exactly 294 rows — "the whole table" and "the uppsc tree" are therefore provably the same set, so the target of 294 was CONFIRMED, not assumed.** `created_at` also split cleanly 294-on-07-05 / 85-on-07-31 with nothing in between, so "absent from the backup" carried no risk of deleting a legitimate post-backup row. **Restored 29 rows** — not 35, because six had been rewritten byte-identically — and **deleted 85 orphans**. `meta` was `{}` in the backup as well, so **nothing beyond title/description text was lost**. Final state, re-queried rather than inferred: uppsc **294**, upsc **202**, **0 rows dated 2026-07-31**, 7,742 question refs + 284 note refs all resolving.

**Founder decisions.** Re-mapping the stranded Article-338 MCQ was authorised, but the agent **correctly refused**: the phantom `polity/constitutional-bodies` was an invented subdivision with no legitimate counterpart, and Article 338 fits three real nodes defensibly, so guessing would have mis-filed a question into the live bank. The founder then chose to delete both the MCQ and the node, landing at 294.

**Root cause, stated precisely.** The accident was caused by **the exact defect class the agent had been dispatched to fix — a valueless flag silently defaulting — reproduced one layer up, in its own test harness.** And the guard shipped for it was **insufficient**: a check of `args.exam === true` structurally cannot see the collapsed-token shape. Closed the same day with three ordered guards in `ingest/syllabus.ts` (proven with a pure `parseArgs` simulation, no pipeline invoked): **(1) reject bare positionals** — `parseArgs` does `if (!a.startsWith("--")) continue`, so `ingest:syllabus upsc` produces no key at all and passes everything; **(2) reject unknown keys** — this is the one that closes the incident; **(3) reject valueless value-flags**, plus positive-integer validation for `--limit-nodes` (NaN is falsy, so `--limit-nodes abc` silently widened a capped smoke test to the full tree). See **D12** — the durable fix is in the shared `parseArgs`, not per-call-site. **✅ D12 SHIPPED 2026-08-01**: those four per-call-site guards have since been deleted as superseded, and the same protection now covers **all 41 arg-parsing CLIs** at once, regression-locked by `pnpm --filter api test:args`.

**⚑ STANDING WARNING FOR EVERY FUTURE SESSION.** `pnpm ingest:syllabus` **with no `--exam`, or with `--exam uppsc`, is a REAL, BILLED, DB-WRITING pipeline** — it LLM-structures and upserts the live UPPSC syllabus tree. `--dry-run` is the ONLY thing that makes it safe, and `--dry-run` is exactly what a misparse silently drops. Before running it, or any other ingest CLI, in a loop or with a variable: **quote the variable, and prefer explicit literal arguments over interpolation.** A refusal is cheap; this pipeline's guards all fire before any I/O, so proving an invocation refuses costs nothing.

> **UPDATE 2026-08-01 (D12 shipped).** A misparse of this shape is now **LOUD, not silent**: the shared `parseArgs` takes a required per-script `FlagSpec` and refuses unknown/collapsed keys, bare positionals, valueless value-flags and bad numerics *before* any I/O — the collapsed-token message names zsh's no-word-split behaviour explicitly. **The advice above still stands** (quote the variable; prefer literals), because the parser makes the failure visible, it does not make a wrong invocation right. It also cannot help a script whose *flags parse fine* but whose values are wrong.
